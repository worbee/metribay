# Metric model

Daily rows are observations, not a gap-filled time series. A missing row is unknown, explicit0 is known. Counts/lines sum only reported rows; coverage and provisional flags describe incomplete intervals. Visitors use independent exact period queries and never sum across days or unrelated sources. Matomo does not return true unique visitors for a custom range, so its preset visitor totals stay unknown. Standing indexed-page counts and present-state GitHub/UptimeRobot metrics use latest observations.

Default cards cover7/30/90 provider-local calendar days including today. Today may be provisional. **Yesterday** is one complete day; a **custom range** is a set of calendar dates (up to 731) read in each source's timezone. Previous comparisons use the adjacent equal-length window. Every metric carries actual bounds, timezone and coverage. Percent change against missing/zero baseline is unavailable. Snapshot metrics (uptime, response time, page speed, open issues, indexed pages) get no growth percentage; they show the difference between the latest value and the last value of the previous period. Monitor status gets neither. A single day's unique visitors is that day's daily value, and a closed calendar month has the provider's month total once it has been read for the monthly report; other non-preset periods have no visitor total.

**Bounce rate** and **average visit duration** are ratios, never stored. Sources store two additive daily parts, `bounces` (visits that bounced) and `visit_duration` (their total length in seconds), next to `visits`. A day's rate is its bounces over its visits; a period's rate is the sum of the bounces over the sum of the visits on the days that have both, never an average of daily rates. A day without either part, or without visits, has no rate and stays a gap. A rate above 100% (parts from different provider counts) is shown as 100%. The change is a percentage of the previous period's rate; bounce rate is lower-is-better. **Conversions** (`conversions`) are completed goals per day and add up like visits; a source records them only when its window has any (see [providers](PROVIDERS.md#audience-breakdowns)).

**Channels** are visits per channel and day (`channel_days`), so any period, custom ranges included, is the sum of its days, compared with the period before. A date's channels are replaced together; a date with no channel rows is known only when the source recorded zero visits that day, otherwise it is missing and the coverage says so. The other breakdowns (`breakdown_rows`) are top lists per stored window: 7, 30 and 90 days ending on the source's day of collection, and the window before each. Yesterday and custom ranges use the closest stored window and say so. Visits and conversions in a list add up to a share of the listed total; visitors do not, so a visitor list shows bars against its largest row and no shares.

**Open issues** uses the latest recorded count in the selected window for each source, never a sum across days. The overview adds those source counts for each project and shows totals across projects; unknown sources remain unavailable in the breakdown, while a recorded zero stays zero. The overview sparkline sums a date only when every source has an observation for it; missing dates remain gaps. The project page charts each source's recorded daily snapshots. Neither view shows a percentage change for this snapshot metric (the project page shows the difference from the previous period's last count), and the current count cannot reconstruct dates before collection began.

Azure DevOps exposes the same `open_issues` key from its open work items, so it shares the column and the snapshot rules. Its `pipeline_runs_succeeded` and `pipeline_runs_failed` are daily sums by finish time; the overview's Commits · PRs column also includes Azure DevOps commits and completed pull requests.

**Items published** (`published_items`) counts RSS/Atom entries by publication date. **New URLs detected** (`new_urls`) counts sitemap URLs first observed after an initial baseline, on their UTC detection date. The first successful catalog, including an empty one, establishes the baseline without counting existing URLs as new. Repeated syncs accumulate that day’s distinct additions; removing and reintroducing a URL does not count it again. Tracking is independent of optional events and survives project transfers. Days without a successful collection stay unknown; no publication history is inferred. The baseline day and today are partial. `lastmod` is retained as modification metadata, not used to count additions. **Published URLs** (`published_urls`) remains the latest current sitemap size, never a sum across days. Feed publications and URL detections remain separate in the overview and the project Content group.

**Release downloads** (`release_downloads`) is the current sum of GitHub release asset download counts. It uses the same snapshot rules as open issues: the latest recorded total in the window, never a sum across days, and no percentage change. The overview adds those totals across a project's GitHub release sources. Missing dates stay empty, because GitHub does not provide a daily history to backfill. WordPress.org `downloads` stays a separate daily sum and is not mixed into this total.

**Followers** (`followers`) is the current follower count of a public Bluesky or Mastodon account. It is a snapshot like release downloads: one value per UTC day, replaced when that day is collected again, the latest recorded count in the window, a difference instead of a percentage change, and no backfill, because neither network publishes a follower history. Days without a successful collection stay empty, and an explicit zero is stored as zero. The overview **Followers** column adds the latest counts of a project's follower sources, so one person following two accounts counts twice. A total over days needs every source to report that day.

**Active users** (`active_users`) are distinct people with any event in a PostHog project. Like visitors, they are a period metric: each day has its own count, and 7, 30 and 90-day totals are separate provider totals counted once per window, never a sum of days or of sources. There is no overview column for them, because the overview adds sources together.

**Key events** (`key_events`) are the daily count of one named PostHog event, summed over days like page views. Each source counts one event; the chart label carries the event name. Different events are never added together.

Overview columns match the metric keys exposed by each source. A future provider that exposes the registered `open_issues` metric joins the same overview column without a provider-specific dashboard change.

All writes validate known metric keys, provider ownership, finite nonnegative numbers, valid dates and percent/status ranges before one atomic transaction. Canonical date-only setters prevent SQLite timestamp text from breaking metric identities. Daily first collected_at is preserved; changed numeric values advance revised_at, and observed_at records latest contact. Snapshot replacement removes omitted same-day readings while retaining present data. Uptime rows carry exact trailing24h window bounds.

Source identities are immutable combinations of provider/resource/timezone. Rename, pause, window changes and project archival retain history. A replaced resource requires a new source. Collectors fetch outside SQL write transactions, then recheck source/credential versions and enable/archive state before persisting. Failures preserve prior observations and expose only safe error categories.

Page speed uses latest, non-additive lab and field snapshots. Lab score is bounded to0–100, timings are milliseconds and CLS is a unitless ratio. The overview selects the lowest score per project and omits score totals. CrUX page and origin keys stay distinct, retain exact 28-day window bounds and p75 metadata in nullable daily_metrics.context, and delete superseded readings when history reports them missing. See [Page speed rules](PAGESPEED.md).
