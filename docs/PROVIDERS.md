# Provider connections

| Provider | Resource configuration | Connection |
|---|---|---|
| Umami | website_id,days; UTC compatibility mode | public HTTPS base_url,username,password |
| GA4 | property_id,days; exact property timezone | service_account JSON, or client_id/client_secret/refresh_token |
| Search Console | site_url,days; America/Los_Angeles | service_account JSON, or OAuth refresh credentials |
| Bing | site_url,days; UTC | api_key |
| WordPress.org | slug,limit; UTC | none |
| GitHub | owner/repository,days, optional deployment environments; UTC | token, or client_id/installation_id/private_key |
| Page speed | public HTTPS URL; mobile/desktop; UTC snapshots | own Google API key, with PageSpeed Insights and Chrome UX Report APIs enabled |
| UptimeRobot | monitor_id; UTC observations | read-only api_key |

Dates and numeric rows are strictly validated. Umami verifies site access before trusting zero-looking stats and independently queries visits/period visitors. GA4 validates metadata and timezone, marks recent dates provisional and rejects sampled, thresholded or restricted reports, and separately requests exact user totals. Search Console combines final/all data states with pagination and explicit finality. Bing decodes .NET dates and keeps traffic/crawl gaps independent. WordPress verifies plugin existence before trusting download counts. GitHub bounds cursor pagination, separates repository activity from productivity claims, and reconciles release events. UptimeRobot validates monitor identity, exact rolling24h windows, response-time sample availability and a shared per-credential request limit.

GitHub imports two kinds of automatic project events. **Releases** are published, non-draft releases inside the collection window; GitHub lists releases by creation date, so collection reads until creation dates fall 30 days before the window and skips older pages. **Deployments** are imported only for the environments named on the data source (at most ten, matched without regard to case), and only from the default branch or a tag; deployments from other branches, or whose branch no longer exists, are skipped. GitHub Actions creates one deployment per job that names an environment, and another set per re-run, so deployments are grouped by the workflow run in their status log URL: each run and environment becomes one event (`run:{id}:{environment}`), dated by the run's last success and linking to the run. A run counts when a deployment succeeded after its last failed one, so a successful re-run counts and a run that failed last does not (a cleanup job that succeeds after a failure still makes the run count). Deployments outside Actions are one event each, dated by their first success and linking to the commit. Titles are `{environment} · {tag or short commit}`. Deployments that GitHub later marked inactive because a newer one replaced them still count. Each sync reconciles both kinds only inside the window it read, so older events remain. Changing the environments deletes the source's deployment events and queues a full import. Reading deployments needs a classic token with `repo` scope, or a fine-grained token or GitHub App with Deployments read access; a GitHub App installation token requests that permission only when environments are set. When GitHub refuses, collection fails with `GitHubDeploymentAccess` instead of silently dropping events; sources without environments never read deployments.

GitHub supplies **Open issues** from its issues-only open count, excluding pull requests. Each sync records the current count on its UTC date when repository issues are enabled; later syncs update that day's snapshot and retain earlier observations. Missing dates cannot be filled from the current count. The overview uses these snapshots for its sortable Open issues column and trend, and the project page shows the full daily chart. See [metric rules](METRICS.md) for totals and gaps.

Connected accounts (the `Connection` model) accept key material, not arbitrary server filesystem paths. Add data source starts from a project and guides provider choice, connected account, resource discovery and confirmation. Saving an account is an explicit step and keeps it under Settings → Connected accounts; unfinished setup state is discarded when the user leaves and is never resumed. Umami resource discovery includes personal websites and websites shared through teams. If the list is empty, check the connected account and its team membership in Umami, then use Refresh list; manual Website UUID entry remains available. Sign-in, access and connectivity failures display safe, actionable messages. Standalone Google browser OAuth appears when the operator configures their own metribay.google client credentials; other hosts may supply a GoogleAuthorization adapter. The shared callback is /integrations/google/callback. Advanced refresh credentials and manual resource entry remain available. GitHub App resource discovery currently requires manual repository entry. Provider errors never expose bodies or credentials. A successful API call verifies that the supplied credential can reach the resource; the hosted service does not silently grant access through a shared operator identity.

Resource lists gray out and disable items already added to the current project, even when that source is paused or another connected account can read the same item. Manual entry and final confirmation reject the same duplicate. This applies to all resource pickers; Page speed keeps mobile and desktop as distinct sources. To track another resource, choose an available item, or start from another project to track the same item there.

Fixture tests exercise all providers offline. A real public WordPress.org smoke passed at initial setup; that does not establish authenticated permissions for the other providers.


## App ownership and authentication

Core never supplies Metribay's provider app credentials. Use your own account API keys, service-account JSON, GitHub personal token or your own GitHub App installation/private key. Resource discovery and collectors remain part of Core. A provider may impose its own limits; Core adds no Metribay service quota.

For Google browser authorization on your **self-hosted server**, register your own Google **Web application** client, enable the Analytics Admin/Data and Search Console APIs, and register the exact callback URL (`http://127.0.0.1:8000/integrations/google/callback` locally). Set `METRIBAY_GOOGLE_CLIENT_ID`, `METRIBAY_GOOGLE_CLIENT_SECRET` and `METRIBAY_GOOGLE_REDIRECT_URI` in the server's protected environment. The UI says “Connect with your Google app”. Service-account and own OAuth credentials also work through the credential form. Google account access to each property is still required. Never ship a confidential Web client secret in a desktop binary; Desktop uses own credentials instead.

Hosts may bind `GoogleAuthorization`, `ConnectionCredentials` and `ProviderRequests` from `Metribay\Core\Contracts`. Defaults use installation-owned Google configuration, decrypt own credentials and permit local provider requests. Runtime collection, discovery and access checks resolve credentials through the host. Every `SafeHttpClient` call invokes the host's request policy, including token exchange and pagination. Policy exceptions fail collection safely without partial metric writes. `ProviderRequestLimit` gives the user a safe retry message.

Managed services store an encrypted reference and user refresh token; the host resolves app secrets server-side and checks access on authorization start, callback and collection. Core rejects payloads containing `managed_app`; changing an edition label cannot unlock the service. Config exports omit **all credentials**, including managed references/tokens. Reconnect with your own account when moving between installations. A host must never expose a credential-resolution endpoint to untrusted clients. Provider apps and public client IDs alone are not a subscription boundary.

## Page speed

Daily Lighthouse tests and separate CrUX page/origin windows are described in [Page speed](PAGESPEED.md). The `PageSpeedCredentials` host contract supplies managed URL-only access where available; the Core default always requires an own-key connection. Missing CrUX traffic is unknown, never zero, and speed scores are excluded from summed overview totals.
